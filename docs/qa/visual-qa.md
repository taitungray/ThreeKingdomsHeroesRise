# 三國：群英再起視覺驗收規範

狀態：MANDATORY QA STANDARD。這裡定義人工視覺驗收流程，不記錄資產完成率或目前缺陷。

預設不因每次小改自動開瀏覽器或截圖；只有使用者要求「測畫面、截圖、視覺驗收、跑版檢查」時才走完整流程。自動化測試不能代替這份人工視覺驗收。

## 1. 驗收前置

- 記錄 commit／工作樹狀態、瀏覽器、DPR、縮放、尺寸、關卡、編隊與速度。
- 清楚區分修改前、修改後；不得拿不同關卡或不同角色的截圖假裝比較。
- console error、資產 404、Canvas frame exception 或戰鬥卡死先判 FAIL，不進入美感評分。
- 戰鬥角色改動必須先通過 `npm run test:combat-assets`，再做逐狀態截圖。

## 2. 基準尺寸

- 390×720：主要手機基準。
- 430×932：高螢幕與 safe area。
- 320×568：窄螢幕降級。
- landscape／max-height 540：旋轉提示或短高降級。

至少以 390×720 做完整流程，其餘尺寸做 HUD、面板、結算與裁切回歸。

## 3. 12 項畫面檢查

1. Alignment：文字、圖示、按鈕、血條與角色 foot anchor 是否在正確基準線。
2. Spacing：是否太擠、太散、碰安全區或遮擋戰場。
3. Hierarchy：戰場、敵人、主要操作、狀態與 meta 的先後是否正確。
4. Composition：焦點與視線是否集中在當前威脅，不被四周 HUD 夾住。
5. Color：是否符合戰場鐵木、軍帳紙卷、朱砂戰令、深色金線。
6. Typography：繁中、字級、字重、對比、單行按鈕與數字穩定性。
7. Asset scaling：角色、敵人、Boss、兵器、坐騎與 icon 比例是否正確。
8. Cropping／alpha：是否裁掉兵器、頭盔或透明邊；是否出現黑框、整格底色、白邊。
9. Layering：覆蓋層、VFX、血條、兵器、角色與 HUD 的 z-order 是否正確。
10. Consistency：同類表面、邊框、陰影、狀態色與角色風格是否一致。
11. Readability：三秒內是否看懂位置、威脅、下一步與成功／失敗狀態。
12. Game style：是否像完整三國像素手遊，而不是 dashboard、debug 畫面或廉價 H5 工具列。

## 4. 戰鬥逐狀態矩陣

每次角色、敵人、Boss、兵器或戰鬥動畫改動，都要保留下列證據：

| 對象 | idle | move／entry | attack 五階段 | hit | death／removed |
|---|---:|---:|---:|---:|---:|
| 我方近戰 | 必測 | 必測 | 必測 | 必測 | 必測 |
| 我方遠程／謀士 | 必測 | 必測 | 必測 | 必測 | 必測 |
| 普通近戰敵人 | 必測 | 必測 | 必測 | 必測 | 必測 |
| 普通遠程敵人 | 必測 | 必測 | 必測 | 必測 | 必測 |
| Boss | 必測 | 必測 | 必測 | 必測 | 必測 |

攻擊五階段為 anticipation、windup、contact、follow-through、recovery。每張圖都檢查身體只畫一次、兵器只畫一次、握點、朝向、輪廓、alpha、血條位置與 VFX 遮擋。死亡後至少再取一張下一 frame／下一波畫面，確認沒有屍體、兵器或影子殘留。

## 5. 覆蓋層與流程截圖

依序捕捉：關卡開始、普通波次提示、敵將預告、Boss 橫幅、底部對話、勝利結算、失敗結算。確認同一時刻沒有兩個中央覆蓋層，敵將卡不遮單位，結算沒有對角 X／穿透線，關閉後 HUD 與焦點恢復。

## 6. 硬錯誤

以下任一項即 FAIL，不以平均分數抵銷：

- 角色、敵人、Boss 或兵器出現黑框、方塊、不透明 Sprite cell、錯圖、重影、雙身體、雙兵器、漂浮、穿模或死亡殘留。
- 攻擊時身體消失、方向錯、武器與手分離；受擊或死亡導致整圖亂跳。
- 敵將預告、Boss 橫幅、對話或結算遮住主要戰鬥區，或多層同時堆疊。
- 按鈕被遮住、必要文字裁切、角色／裝備拉伸、z-index 穿透、狀態只靠顏色。
- 獎勵重複發放、戰鬥卡死、console error、資產 404、破壞 reduced-motion。
- 一眼看出是網頁：雙排迷你 icon、8–11px 必要標籤、關卡名截斷、資源列小於 14px、介面比戰場搶眼。

## 7. 角色分工與狀態圖包

- 資深美術先判定角色、背景、icon、材質、光向、比例與像素風格是否一致，標記 Keep／Adjust／Replace。
- 資深 UI 再判定畫面目標、資訊層級、構圖、文字與狀態對比、觸控及響應式，不能用「沒有 overflow」代替品質判定。
- 主要介面需包含 normal、pressed、selected、disabled、loading、error、locked、資源不足、completed／claimed 與滿級狀態（適用者），並保存頂部、中段、底部及捲動過程。
- 角色抽樣至少包含四兵種、長短名字、已擁有、未解鎖與滿級預覽；全 50 名自動化檢查仍要另外執行。
- 若由同一執行者負責兩種角色，報告必須拆成兩段獨立判定。完整責任與判定依 [遊戲品質審查與四層驗收規範](../standards/game-quality-review.md)。

## 8. 結果與證據格式

結果只能是：

- `PASS`：無硬錯誤，完整矩陣與尺寸均有證據。
- `PASS WITH ISSUES`：無硬錯誤，但有不阻擋的 polish 項目；列出 owner 與後續。
- `FAIL`：任一硬錯誤、console／流程錯誤或證據缺失。

回報必須包含：受測版本與環境、尺寸與頁面、測試資料、逐狀態截圖路徑、12 項結果、硬錯誤、console 摘要、修改前後比較、最多 5 個優先修改建議，以及尚未執行的瀏覽器／實機範圍。
