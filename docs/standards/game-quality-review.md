# 遊戲品質審查與四層驗收規範

狀態：MANDATORY STANDARD。本規範是「遊戲好不好」的單一權威流程；功能測試、視覺驗收與發布矩陣仍分別依 `docs/qa/` 執行。自動化通過只代表受測斷言成立，不代表遊戲好玩、好看、好懂或可發布。

## 1. 核心原則

- 功能 QA 與遊戲品質 QA 必須分開判定；不得用 console 無錯、DOM 存在或 50 名角色無 overflow 代替玩家體驗。
- 第一章垂直切片優先於全量內容：先驗收 8 名武將、10 關、3 種普通敵人、1 名精英、2 名 Boss 與完整養成→戰鬥→結算→再戰循環。
- 資深玩家、資深企劃、資深美術／UI 與工程 QA 要分別產出判定；一個角色的 PASS 不得抵銷另一角色的 FAIL。
- 同一執行者可以依序模擬多個專業角色，但報告必須分段、列證據，並標記「角色模擬審查」；沒有真人盲測時不得宣稱已完成玩家盲測。
- 每輪只修最高優先的 3–5 個問題，再用同版本、同帳號與同場景重測。禁止一次擴張大量系統後才驗收。

## 2. 第一層：資深玩家盲測

真人測試者不看操作說明與預期答案，從空帳號連續遊玩 15–30 分鐘並錄影。至少再用中期帳號、零資源帳號與含鎖定角色的帳號各跑一次主要操作。

必記錄：

- 10 秒內是否知道下一步；第一分鐘是否出現真正決策。
- 第一次停頓、誤點、回頭、跳過文字、找不到操作、感到無聊或誤解規則的時間點。
- 是否能獨立完成登入／教學、編隊、養成、戰鬥、Boss、勝敗結算、重試／下一關。
- 快速連按、亂序操作、返回、切背景、重整與重複遊玩後是否仍理解狀態。
- 測試者原話、畫面時間碼、預期、實際結果與玩家影響。

真人盲測尚未執行時，品質狀態最多只能寫「缺少證據」，不得以自動化或代理角色推演補成 PASS。

## 3. 第二層：資深企劃審查

每個畫面與系統都要回答：

- 唯一主要任務與下一步是什麼；是否有重複入口、重複資訊或未完成功能。
- 哪些資訊會改變決策；哪些只是裝飾、數字堆疊或假深度。
- 行動→即時回饋→獎勵／損失→決策→下一輪是否完整。
- 每 30 秒有多少真正選擇；是否大量等待、唯一最佳解、無意義資源或必買升級。
- 關卡壓力是否來自新行為／組合／資源選擇，而非只加 HP 與傷害。
- 新帳號能否在不看文件的情況下理解目標、勝負、失敗原因與成長方向。

企劃輸出必須包含 Keep／Remove／Simplify／Fix、P0–P3、玩家影響、驗收案例與第一章範圍外 Hide／Lock 決策。

## 4. 第三層：資深美術與 UI 審查

固定證據尺寸為 320×568、390×720、430×932；390×720 跑完整流程，其餘做 HUD、面板、結算與裁切回歸。每個主要介面至少保存：

- normal、pressed、selected、disabled、loading、error、locked、resource insufficient、completed／claimed、max-level（適用者）。
- 面板頂部、中段、底部與捲動過程，不得只取最好看的首屏。
- 步兵、騎兵、弓兵、謀士、長名字、短名字、已擁有、未解鎖與滿級預覽角色。
- 戰鬥 idle、move、attack 五階段、hit、death／removed、敵將預告、Boss、勝利與失敗結算。

美術審查負責角色／背景／icon／材質／光向／比例／像素風格的一致性；UI 審查負責目標、層級、構圖、對比、字體、間距、觸控、狀態與響應式。兩者共用同一 Visual Contract，但必須各自判定。

任一角色錯圖、黑框／方塊、武器脫手、必要文字看不見、主要操作不明、介面比戰場搶眼或明顯像網站 dashboard，直接判 FAIL，不以平均分數抵銷。

## 5. 第四層：工程與自動化 QA

依 `docs/qa/qa-test-matrix.md` 執行語法、資產、功能、輸入、生命週期、存檔、網路、source／`www`、瀏覽器與 Android 實機測試。自動化全 50 名角色適合抓資料缺漏、overflow、控制尺寸與例外；人工代表角色適合判斷視線、品質、辨識與遊戲感，兩者都要保留。

## 6. 角色責任與獨立判定

| 角色 | 必須回答 | 最低證據 |
|---|---|---|
| 遊戲總監 | 核心循環與第一章是否值得繼續製作 | 四層結果、範圍決策、最終 gate |
| 資深玩家 | 不看說明能否玩懂、是否想繼續 | 真人錄影、時間碼、原話、任務結果 |
| 資深企劃 | 是否有決策、節奏、回饋與多餘系統 | 逐畫面／系統 Keep／Remove／Fix |
| 資深美術 | 所有資產是否像同一款完成品 | 固定尺寸圖包、Keep／Adjust／Replace |
| 資深 UI | 是否好懂、好按、好讀且像遊戲 | 狀態圖包、三秒測試、尺寸／對比證據 |
| 工程／QA | 功能、資料、生命週期與平台是否可靠 | Given／When／Then、log、命令與實機資料 |

## 7. 缺陷與迭代格式

每個問題記錄：受測 commit、環境、帳號／角色／關卡、重現步驟、畫面或時間碼、預期、實際、玩家影響、P0–P3、owner、修正方案與重測結果。

迭代順序固定為：定義本輪目標 → 建置 → 四層觀察 → 各角色獨立判定 → 合併最高優先 3–5 項 → 修正 → 同條件重測。

## 8. 判定與完成門檻

- `PASS`：四層必測範圍均通過，P0／P1 為零，證據完整。
- `PASS WITH ISSUES`：P0／P1 為零，只剩不阻擋理解、操作與品質的 P2／P3，且有 owner。
- `FAIL`：任一 P0／P1、任一專業角色重要項目失敗、核心流程不好懂／不好玩、視覺硬錯誤、實機條件未通過或必要證據缺失。

「自動化全部通過」不能提升為品質 PASS；「尚未真人盲測」與「尚未 Android 實機」必須明列，發布前不得省略。

## 9. 產圖決策

只有功能、資訊架構與 Visual Contract 穩定後才產圖。每個產圖需求需寫明用途、尺寸、STYLE LOCK、角色／物件、構圖、材質、光向、透明背景、禁止內容、normal／pressed／disabled 等變體與驗收方式；中文字、價格、關卡名與動態數值不得烘焙進圖片。

## 10. 活動頁面追加門檻

日後製作簽到、節慶、挑戰、兌換、累積進度、戰令或任何限時活動頁，都必須完整套用本規範，不得以活動時程短、只用一次或屬營運內容為由降低品質。

活動開始製作前，企劃必須先鎖定：

- 玩家目標、核心操作、事件循環、開放條件與為何值得參加。
- 起訖時間、時區、預告／開放／結束／補領期，以及時間來源。
- 任務條件、進度算法、獎勵表、領取次數、重複發獎防線與資源來源／消耗。
- 新玩家、中期玩家、已完成、未達成、錯過、無網路與活動結束後的處理。
- 不參加活動的玩家是否仍能正常遊玩；禁止用刻意做壞主流程逼迫參加。

活動 UI 必須：

- 三秒內看懂活動目的、剩餘時間、目前進度、主要獎勵與唯一主要 CTA。
- 使用既有 Visual Contract；活動主題可以換裝飾與重點色，不得變成另一款遊戲或通用網頁 banner。
- 完整支援 preview、open、locked、insufficient、completed、claimed、sold out、ended、loading、error、offline 與 retry（適用者）。
- 倒數、價格、進度、任務與獎勵使用真實資料；不得展示假倒數、假排名、假可領取或未配置服務。
- 中文字、倒數、價格、進度與動態獎勵不得烘焙進圖片；產圖只能提供背景、角色、裝飾、icon 與可重用材質。

活動 QA 至少覆蓋開始前一秒、開始時、結束前一秒、結束時、補領期、時區切換、背景／前景、重整、斷線／重試、連點領取、回呼重送、存檔重載與多尺寸。任何重複發獎、錯誤倒數、活動結束仍可操作、必要狀態缺失或獎勵說明不一致，直接判 FAIL。

活動頁仍需遊戲總監、企劃、美術、UI、QA 各自判定；沒有四層證據、真人盲測與實機條件時，不得宣稱活動完成或可上線。
